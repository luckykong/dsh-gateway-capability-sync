## 问题清单

| 编号 | 优先级 | 原始问题与影响 | 修复结果 |
| --- | --- | --- | --- |
| GCS-01 | 高 | `findEntry()` 在找到准确 entryId 前即可按包名返回，可能修改错误 Loader。 | 优先精确匹配并核对包名；仅默认 ID 允许唯一候选兜底，多个候选或自定义 ID 不存在时报错。 |
| GCS-02 | 高 | `missing` 只检查模型 compat，新增模型字段可盖过 provider 的手工设置。 | 按模型和 provider 的有效字段逐项判断缺失，保留显式 false。 |
| GCS-03 | 高 | 不检查 API 就写入 completions 专用 compat；Responses 等路由可能校验失败。 | 只在明确为 openai-completions 时写这些字段；协议未知时保留配置并给出提示。 |
| GCS-04 | 中 | 已有 reasoningEfforts 时不补 compat；always 又不更新已有 compat，与文档不符。 | reasoningEfforts 和 compat 分别应用 missing/always；按实际值判断是否修改。 |
| GCS-05 | 中 | 缺少能力元数据被归一为 false，always 会删除已有图片和思考能力。 | 保留支持、不支持、未知三种状态；未知不覆盖，明确 false 才可禁用。 |
| GCS-06 | 中 | 查询继承模型后只修改 override，导致静默跳过并报告已是最新。 | 从 Host 当前完整配置派生新配置，支持继承来源的模型，保留其他 provider。 |
| GCS-07 | 中 | 某个 provider 的 DNS、超时、JSON、凭证异常会使整轮中止。 | 各 provider 单独捕获异常；成功的 provider 仍可同步，报告部分失败。 |
| GCS-08 | 中 | 停用插件只设标记，不取消请求；已运行任务仍可能提交配置。 | 使用取消信号，在请求后及 edit 回调中检查停用状态，清理定时器。 |
| GCS-09 | 中 | 同步中的重载事件直接复用 inFlight，事件可能丢失。 | 合并待处理的重载请求，本轮完成后重新读取最新配置；普通并发命令共用本轮结果。 |
| GCS-10 | 中 | 第 9 秒只扫描一次，慢同步后报告过时，手动同步也不重新扫描。 | 每轮同步与 Loader 重载完成后扫描；没有自动同步时保留启动扫描。 |
| GCS-11 | 中 | 明确返回有效档位却省略 supports_reasoning 时，思考能力被忽略。 | 有效档位或默认档位可推断支持；显式 supports_reasoning:false 优先。 |
| GCS-12 | 低 | 版本号不一致且没有回归测试入口。 | 源码读取包版本；加入 Node 原生测试命令和关键行为回归。 |
| GCS-13 | 低 | 失败或跳过也显示 already up to date；debug:false 仍显示报告路径；扫描早期错误未落盘。 | 区分更新、无变化、跳过、失败、取消；按开关显示报告路径，扫描错误同样写报告。 |
| GCS-14 | 中 | 原代码混合 inherited/override，但 configEditor 写入的是完整 raw config；错误拼接可能恢复已移除的 provider。请求期间地址变更也可能写入旧结果。 | 以 entry.options.config 和 edit 回调 current 为准；提交前核对 provider 请求配置，变化时跳过旧结果并重查。 |

## 实施约定

- 不自动新增网关模型；没有本地 models 列表的目录路由明确报告跳过。
- `missing` 保留模型和 provider 已有的显式能力；`always` 仅刷新网关明确声明的能力以及适用协议的两个 compat 字段。
- `supports_reasoning:true` 但无有效档位时，不凭空构造档位、不关闭已有思考能力。
- 继承列表需要补全时，写入 Host 要求的完整配置；列表会固定在 profile，后续上游列表变化需重新导入。
- 不自动清理以前写入的不适用协议的 compat，因为无法判定它是否来自手工设置；这类存量配置需要单独修复。
- `missing` 同时保留 provider 显式 defaultInput。未知协议只同步通用能力，提示未补全 completions 专用 compat。
- 自定义 debugFile 的扫描报告使用独立文件名，并自动创建父目录；debug:false 关闭报告和扫描。
- 同时修正 Authorization 大小写导致的重复请求头，以及退出 HMR 上下文时发生同步异常后重复执行操作的问题。

## 1.1.1 追加修复（真实环境复现驱动）

现象：新增模型 `cn:mimo-v2.6-pro` 后，本地配置长期缺少 `input`。网关侧
`withImages: 22`（22 个模型全部声明支持图片），插件也正确算出补全内容，
但报告为 `status: failed` / `wrote: false`，错误 `HMR transactions cannot be nested`，
且重试 5 次全部失败。

排查结论分两部分：

- **能力识别没问题**：插件不依赖任何内置能力库，只读网关 `/v1/models`
  的 `supports_images` 等字段（字段缺失或非布尔即视为未知，不猜测）。
  mimo 的数据也确实是 `supports_images: true`。
- **写入被事务冲突阻断**：`configEditor.edit` 在 `hmr.executing` 仍有值时直接
  reject。`exit()` 能清掉插件自己继承的上下文（已用 `AsyncLocalStorage`
  实测确认，包含 `await` 续体），所以失败来自「调用瞬间存在邻近事务」。

本轮修复：

| 编号 | 问题 | 修复 |
| --- | --- | --- |
| GCS-15 | 无需写入 + 有 provider 连不上时被标为 `failed`，与实际（配置已是目标状态）不符 | 引入 `attemptedWrite`；只有真正尝试写入失败才 `failed`，无需写入时保留 `up-to-date` |
| GCS-16 | 嵌套事务错误被当作永久失败，且 `retriesLeft` 耗尽后不恢复 | 统一 `isNestedTransactionError()`；写入成功后重置重试预算 |

验证：

- `npm test` 47/47 通过（原 44 项 + 3 项新增）。
- 变异测试：还原 status 判定后「up-to-date 不应报失败」用例失败；移除嵌套错误识别后
  重试用例失败。两项修复均有对应用例兜底。
- 曾尝试引入「写入前探测 store 并原地等待」的防御逻辑，实测该探测在插件自持上下文下
  恒为假（`exit()` 已清空），属不可达分支且测试无法覆盖，故在定稿中移除，只保留
  经证实有效的改动。
